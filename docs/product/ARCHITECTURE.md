# Product boundary and decisions

The product adapter reuses the approved Nest controllers, SQL commands, B3 immutable commercial artifacts and B4 serializable allocation ledger. Original migrations 0001–0015 remain byte-identical. Additive product migrations use a separate contiguous checksum registry. A private Next bridge owns browser cookies and fixed route allowlists; Nest is not directly public. The edge overwrites peer headers. Authentication, API, worker and migration database roles have separate secrets/EXECUTE boundaries. The web has only its bridge key. Browser identity, slots, price/policy data and payment success are never authoritative.

Customer identity is the canonical verified Iranian mobile lookup (HMAC), with authenticated encrypted contacts and OTP payloads. OTP denial commits attempt/rate counters; expired/consumed challenges cannot be reused. Password verification uses bounded scrypt work. Privileged sessions require the role's current assurance and credential generation, idle/absolute validity and unrevoked assignments. MFA counters/recovery codes are single-use. A management role does not replace the customer's separately scoped self-booking permission. Test provenance cannot be cleared or imported into a production realm. Offline operator invitations are the only initial administrator bootstrap; no production local-login controller is registered.

The planner resolves current server availability, necessary eligible staff/resources, timezone/DST and complete current offering configuration. Quote/acceptance hashes remain B3/B4 canonical contracts. The measured membership-join materialization reduces redundant predicate work without changing the complete commercial artifact; original-versus-new execution is compared. Product transaction retries replay the entire SERIALIZABLE unit only for 40001/40P01, with bounded jitter, preserving legacy retry behavior. Scheduling changes retain the canonical lock and fail closed for live allocations in affected branches/resources/staff; an unrelated branch no longer freezes the entire business. Within an affected branch the review guard remains deliberately conservative, including metadata-only changes; there is no displacement override.

Payments bind one merchant intent to an accepted revision and its exact integer Rial deposit. Browser callbacks can only wake verification of an already bound authority/state. The worker independently verifies provider amount/currency/authority/reference/evidence, then records an immutable receipt and atomically confirms eligible unexpired capacity. Duplicate/late results cannot recreate allocations. Late money is recorded for refund review. A definitive failed intent is not silently replaced; unknown results require reconciliation and must not cause a new charge. Refund requests are authorized and bounded by verified paid money and frozen accepted terms; only independent provider evidence marks a refund verified. The live gateway is explicitly unconfigured until selected. No settlement claim is inferred from a redirect, screenshot or UI label.

The durable delivery queue uses leases, SKIP LOCKED bounded batches, semantic deduplication and separately versioned/frozen notification templates. OTPs are decrypted only at dispatch. Acknowledgement loss is retried automatically only for replay-safe adapters. A non-idempotent ambiguous live SMS send stays UNKNOWN for reconciliation. DELIVERED currently means provider acceptance, not a delivery report from the handset. Reminder/no-show settings are disabled until configured. Workers suppress reminders for bookings already in salon operations. Provider secrets and raw payloads are never logged.

The existing single-provider MVP remains the supported selection contract. The revision/segment model can represent different staff per service later, but public selection currently requires one staff member qualified for every selected service. Different service-level financial policies remain a resolver conflict unless an explicitly configured compatible strategy exists. There is no invented blended deposit/refund rule. Zero-deposit rescheduling preserves the supported B4 same-items/same-terms restrictions; paid changes require a future owner/provider-approved financial transition.

The CMS remains manual and rights-gated, with private local/S3 originals, bounded ZIP/media processing, immutable variants and explicit publication. The public fallback uses owner-approved SVG geometry/system fonts rather than internal client photos or fictional before/after pairs. Internal review assets remain in the private checkout. Container packaging physically excludes them; the final image is hash-audited. No production credentials, fixtures or synthetic accounts are bundled.

Operational choices still requiring the owner or external provider are actual staff/hours/prices/policies, second-branch details, media rights/content, approved SMS sender/template/account, selected gateway/refund/reconciliation contract, domain/certificates/hosting/private bucket and backup/alert retention targets, and final production acceptance. These are configuration/acceptance boundaries, not a proposal to begin another development phase. Automated key rotation, multi-provider selection and paid financial rescheduling are deliberately separate architectural contracts; existing accepted records must never be silently reinterpreted.

Primary contracts: [PostgreSQL TLS](https://www.postgresql.org/docs/18/ssl-tcp.html), [serializable retries](https://www.postgresql.org/docs/18/transaction-iso.html), [pg_dump snapshots](https://www.postgresql.org/docs/18/app-pgdump.html), [Kavenegar](https://kavenegar.com/rest.html), [Node crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html), [RFC 6238](https://www.rfc-editor.org/info/rfc6238/), [Next CSP](https://nextjs.org/docs/15/app/guides/content-security-policy), [Docker secrets](https://docs.docker.com/compose/how-tos/use-secrets/). No unselected live payment endpoints are inferred.
